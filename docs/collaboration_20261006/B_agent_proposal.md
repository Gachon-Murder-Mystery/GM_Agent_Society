# GM 진행 상황 공유 및 플레이어 에이전트 연결 방식 협의 제안

수신: 황규한님 · 플레이어 에이전트 담당(B)

작성: 박천웅 · GM 및 GM↔agent 상호작용 담당(C)

작성일: 2026년 10월 6일

규한님, GM 쪽에서 어떤 입력·출력을 생각하고 준비했는지와 다음 연결에서 같이 맞춰 보고 싶은 내용을 정리했습니다. 저는 GM이 agent의 판단을 대신하기보다 현재 단계와 상황을 안내하고, 엔진이 확정한 결과로 진행과 정보 소유를 기록하는 역할을 생각하고 있습니다. 아래 내용은 연결을 위해 마련한 제안이니, 현재 agent 설계에 더 자연스러운 방식이 있다면 알려 주시면 GM 쪽 형식을 맞춰 보겠습니다.

## GM이 안내하려는 내용과 역할 경계

게임 시작에는 본인의 직업·스테이터스·스킬·성향·선택 목표를 전달하고, 각 단계에서는 현재 cycle/phase, 허용 행동, 남은 행동 횟수, 위치와 상호작용 대상을 안내하도록 준비했습니다. 이동 전에는 전체 위치를, 이동 후에는 같은 공간의 대상을 알려 주는 흐름입니다.

무엇을 조사하거나 의심할지, 추리를 시도할지 생략할지, 어떤 정보를 공개할지는 agent의 판단으로 두었습니다. 행동은 agent가 엔진에 직접 요청하고, GM은 엔진의 완료 결과로 전원 진행을 확인합니다. GM이 가진 전체 감독 원장을 agent의 입력에 넣는 대신 본인 정보와 명시적 공유 정보를 구분하는 방향입니다.

## 현재 GM 쪽에서 진행한 내용

| 준비한 영역 | 현재 확인한 범위 | 규한님과 맞춰 보고 싶은 부분 |
|---|---|---|
| 배분·단계·상황 안내 | 가변 인원별 캐릭터 조합과 PhaseNotice 생성, 위치·대상·허용 행동 출력 | agent가 실제 수신하기 편한 입력/호출 형식 |
| 단계 완료·정보 원장 | 모의 엔진에서 결과·소비·보유 정보 기록과 다음 단계 진행 | 실제 엔진 결과와 agent의 수신 상태 연결 |
| 실제 구성요소 연결 | B의 키 없는 파서가 만든 명령을 A 함수에 넣고 C가 획득 단서 2개 기록 | 사람이 입력을 정하는 해석기에서 자율 선택·결과 수신 루프로 확장 |
| 공통 데이터 의미 | 이동·준비·지목 본문의 왕복 변환과 단서의 제외 의미 보존 | agent 기억에서도 같은 정보 ID와 의미를 사용하는지 확인 |
| 장애·역할 전환 | 모의 환경에서 NPC/시체/대리 GM 구분과 GM 인계 호출 지점 | agent 런타임의 중단·수신·역할 전환 접점 |

실제 부분 연결은 오프라인 파서와 고정 주사위로 확인했습니다. 자율 판단, 실제 LLM 입력, 다중 agent의 한 사이클과 실제 장애 전환까지 확인한 상태는 아닙니다. 현재 안내는 GM에서 dict로 만들 수 있지만 B가 실제로 받는 전송·수신 루프는 다음 연결에서 맞춰야 합니다.

## 정상 agent 간 상호작용의 현재 작업 전제

질문자는 같은 공간의 상대를 지정해 엔진에 question을 요청하고, 상대는 자기 보유 정보 중 공개 후보나 거절 의사를 엔진에 제출하는 흐름입니다. 엔진은 소유 여부와 직업·성향·주사위 규칙을 적용해 최종 전달 정보를 확정하고, 질문자와 GM은 같은 최종 결과를 받습니다.

상대의 응답은 별도 이동·탐색·추리 행동을 소비하지 않는 수신 처리로 준비하고 있습니다. 자신의 행동을 이미 쓴 경우에도 상대에게 답할 수 있는 방향입니다. NPC/장애 NPC와 시체는 B의 자율 응답을 기다리지 않고 엔진이 각각 수동 정책과 조사 판정으로 처리합니다.

이 전제를 유지하면서 B의 실행 구조에 더 적절한 수신·응답 방식이 있다면 어떤 구성이 좋을지 의견 부탁드립니다. 저는 공개 판단이나 추리 내부 로직을 대신 구현하기보다, 필요한 상황 안내와 진행·장애 신호 수신을 GM 쪽에서 맞추겠습니다.

## 먼저 같이 확인해 보고 싶은 작은 연결

같은 사건에 2명 이상을 연결해 GM 안내를 실제 수신하고, 각 agent가 이동 → 탐색 → 추리 생략을 선택하는 한 사이클을 먼저 확인해 보면 어떨까요? 단서가 생기면 엔진 결과·agent 기억·GM 원장에 같은 ID가 남는지, 다른 agent에게 아직 공개하지 않은 정보는 전달되지 않는지 같이 보고 싶습니다.

제안한 메서드나 필드 이름을 그대로 쓰기보다 현재 B 구조에 맞게 대응할 수 있다고 생각합니다. 우선 받고 싶은 안내·관찰 예시, 행동·응답 출력 예시, 수신 접점과 대기 방식, 제안 순서에 대한 의견을 알려 주시면 그 기준으로 GM 쪽을 조정하겠습니다.
