# GM 진행 상황과 공통 연결 기준에 대한 협의 제안

수신: 이재형님(A), 황규한님(B)  
작성: 박천웅 · GM 및 GM↔agent 상호작용 담당(C)  
작성일: 2026년 10월 6일

재형님, 규한님, 제가 준비한 GM의 범위와 다음 연결에서 함께 맞춰 보고 싶은 기준을 공유드립니다. 서로 같은 사건·행동·정보를 같은 의미로 사용하는지 확인하는 것이 이번 연결의 중심이라고 생각합니다. 제가 준비한 임시 형식과 흐름을 설명드리고, 각자 개발 중인 구조에서 더 적절한 방식이 있는지 의견을 받아 GM 쪽을 맞추고 싶습니다.

## 무엇을 염두에 두고 작업했는지

기존 데모와 룰북을 바탕으로, 한 사건에서 가변 n명의 agent가 이동 → 탐문·탐색 → 추리로 진행하는 GM을 준비했습니다. 추리는 도전하거나 생략할 수 있고, 오답 사망과 기술 장애는 별개로 표현했습니다. 정상 agent는 판단 주체, 장애 agent는 정보·직업·성향을 유지하는 수동 NPC, 사망 캐릭터는 정보 파편을 조사하는 시체로 구분했습니다.

GM의 직접 작업 범위는 배분·턴·상황 안내, 수신과 진행 확인, 정보 소유 원장, 장애 조정과 감독 기록 인계입니다. 행동 선택과 공개 의사는 B, 공식 상태와 규칙 판정은 A의 결과를 받아 연결하는 방향입니다. 저는 A/B 내부 구현을 대신 바꾸기보다 각 담당자가 제공하는 접점에 GM의 입력·출력을 맞추고자 합니다.

정상 agent 간 상호작용은 현재 GM 작업에서 ‘GM 안내 → B의 엔진 요청 → 상대 B의 공개/거절 판단 → A의 검증·판정 → 요청자와 GM의 동일 결과 수신’을 전제로 사용하고 있습니다. 상대 응답은 별도 능동 행동을 소비하지 않는 수신 처리입니다. 이 전제를 구현하는 접점과 메시지·대기 방식은 각자의 구조를 보고 함께 조율하면 좋겠습니다.

## 어디까지 진행됐는지

| 구분 | 현재 산출물·확인 내용 | 해석할 수 있는 범위 |
|---|---|---|
| GM 핵심 코드 | 캐릭터 조합 배분, 단계 안내·전환, 소유 원장, 장애·대리 GM 호출 지점 | C의 모의 환경에서 처리 흐름 준비 |
| 임시 입력·출력 | contracts.py, io_schema.json, 데모/룰북 기반 catalog와 예시 메시지 | 공통 형식으로 검토할 기준안; A/B 채택은 별도 확인 |
| 실제 구성요소 점검 | B의 오프라인 파서 → A의 실제 함수 → C 관찰 저장, 획득 단서 2개 전달 | 단일 플레이어 구성요소 연결; 사람이 정한 입력과 고정 주사위 사용 |
| 같은 의미의 데이터 | 카탈로그 ID 일치, 이동·준비·지목 본문 3개 왕복 변환, 단서 의미 보존 | 해당 명령·단서의 대응 확인; 실제 다중 agent 통신은 미확인 |
| 테스트 기록 | 의미 검사 9개, 실제 어댑터 검사 6개, 모의 GM 검사 22개, 총 37개 통과 | 계약 부재를 감지하는 검사도 포함; 전체 통합 성공을 뜻하지 않음 |
| 다음 실제 연결 | 실제 전송·수신, 자율 판단, 다중 agent의 한 사이클, 실제 장애 감시 | 각 접점이 준비되면 함께 확인할 작업 |

원격 main에서 확인한 내용을 기준으로 작성했으며, 아직 공유되지 않은 개발 작업량을 평가한 문서는 아닙니다. 기존 형태와 다른 기능을 개발 중이시라면 그 구조와 가능한 접점을 알려 주시면 검토 기준을 갱신하겠습니다.

## 제가 GM 쪽에서 이어서 준비하려는 내용

아래는 제가 맡을 작업과 그 연결을 위해 필요한 정보입니다. A/B의 구현 순서를 지정하기보다, 먼저 제공 가능한 명세·예시부터 받아 준비하고 싶습니다.

| 항목 | GM 쪽에서 준비하려는 내용 | 현재 상태·먼저 필요한 요소 | 함께 확인하고 싶은 의견·대안 |
|---|---|---|---|
| C01 · P0 | 엔진 접점에 맞는 GM 호출·수신 어댑터 | 모의 포트·부분 어댑터 있음; A의 생성/관찰/이벤트/제어 명세 | 실제 구현 전에 예시 응답이나 함수 명세를 먼저 받아 대응표를 만들면 어떨까요? 기존 접점이 있다면 그쪽으로 맞추겠습니다. |
| C02 · P0 | n명 명단·주소 관리와 배분·단계·상황 전달 | 안내 생성 있음; B의 수신 접점/인스턴스 ID와 A의 관찰/캐릭터 정보 | B에서 등록하는 방식과 GM에 주소를 주는 방식 중 어느 쪽이 편할까요? 전달 방식도 수신 구조에 맞추겠습니다. |
| C03 · P0 | 실제 완료 결과를 소유·행동 원장에 반영 | 모의 원장 있음; A의 완료/조회와 감독 소유 상태 | 이벤트 수신과 상태 대조 중 어떤 정보를 먼저 제공할 수 있을까요? 두 자료가 다르면 확인할 기준도 맞추고 싶습니다. |
| C04 · P0 | 안내·상호작용 절차와 공통 메시지 대응 | 기준안·검사 도구 있음; A/B 기능·버전·수신 명세 | 고정 메서드 이름 대신 각자의 예시를 대응해 보는 방식은 어떨까요? 추가로 받고 싶은 GM 안내가 있다면 알려 주세요. |
| C05 · P1 | 실패 신호 수신, GM 통신 재시도·복구 요청·장애 확정 조정 | 현재 수동 장애 주입; 런타임 신호와 A의 NPC 전환 접점 | 먼저 명시적 실패 신호부터 연결하고 시간 기준은 이후 맞추면 어떨까요? 현재 감시·복구 장치가 있으면 활용하고 싶습니다. |
| C06 · P1 | 후임 선출 결과 전달과 GM 서비스·감독 기록 인계 | 모의 인계 있음; A의 권한 변경, B의 역할 전환, 공유 감독 저장소 | 역할 전환 시 필요한 진입 정보나 저장소 접근 방식을 알려 주시면 GM 측 인계 묶음을 준비하겠습니다. |
| C07 · P1 | 이벤트 누락 확인, 재조회, 상태·원장 대조 | cursor/재수신 있음; 연속성 검사는 보완 예정, A의 순서/재조회/snapshot 기준 | 순번, 로그 위치, 상태 버전 중 제공 가능한 기준이 있을까요? 그 기준으로 복구 절차를 맞추겠습니다. |
| C08 · P0/P1 | 미완료·상대 응답 대기·완료 상태 추적 | 전원 완료 장벽 있음; A/B의 진행 신호와 대기/완료 의미 | 진행 상태를 조회할지 통지받을지 함께 정하면 어떨까요? GM이 알아야 하는 최소 상태를 먼저 맞추고 싶습니다. |

실제 접점이 준비되기 전에는 명세·예시와 mock으로 GM 입력·출력 및 절차를 준비할 수 있습니다. 그 결과는 GM 준비로 기록하고, A/B의 실제 기능과 연결한 확인 결과는 별도로 남기겠습니다.

## 같이 맞춰 보고 싶은 공통 자료

다음 표에서 이미 사용 중인 게임 흐름과 상호작용 전제는 GM이 염두에 둔 내용으로 설명하고, 구현 표현·접점·아직 없는 수치는 협의 항목으로 두었습니다. P0/P1/P2는 첫 기본 연결·전체 흐름·추가 요소를 구분한 제안 순서입니다.

| 항목 | 현재 GM이 염두에 둔 기준 | 선결 자료 | 의견을 여쭙고 싶은 부분 |
|---|---|---|---|
| D01 · P0 | 같은 사건/행위자/행동/단서/완료/공개 범위를 추적 | 기존 사전·schema·예시, 각 접점 명세 | 현재 ID와 결과 예시를 같이 놓고 대응해 볼까요? 이름이 달라도 같은 의미가 연결되면 GM 쪽을 조정하겠습니다. |
| D02 · P0 | 한 탐문은 한 행동으로 추적하고 check→roll도 같은 작업의 단계로 표현 | phase/action_id/완료 정의, 데모 pending 예시 | 단일 최종 결과와 pending→최종 결과 중 편한 구성이 무엇인가요? 이중 소비 없이 완료를 확인할 형태를 맞추고 싶습니다. |
| D03 · P1 | 정상 B가 공개 후보/거절을 판단하고 A가 공식 검증·판정 | 정보/객체 ID, 직업·성향 정책, 보유 검증 | 응답 메시지와 정보가 없는 완료 표현을 어떻게 구성할까요? 각자의 현재 처리 구조를 듣고 싶습니다. |
| D04 · P1 | 상대 응답은 능동 행동을 추가 소비하지 않으며 자기 행동 중에도 수신 | 대기/완료 의미, 런타임 신호 명세 | 응답 진행·미응답을 어떤 신호로 알려 주는 것이 편할까요? 시간 수치는 임의로 정하지 않고 함께 맞추겠습니다. |
| D05 · P1 | 같은 공간의 질문/응답과 전체 공유를 구별 | 개인/감독/공개 범위, 공유 접점 | 첫 연결에서 지원할 공유 범위를 어디까지 잡으면 좋을까요? 다른 전달 범위가 있다면 소유·공개 기록을 어떻게 남길지 같이 보겠습니다. |
| D06 · P1 | 엔진 단서와 대화 주장·추측을 구별해 기록 | 원본 정보 ID/제외 의미, B의 기억 구조 | 원본 정보와 추론 결과를 어떻게 구분 중인가요? 거짓말 허용 같은 추가 정책은 별도 의견을 받아 정리하고 싶습니다. |
| D07 · P1 | 장애·사망·GM 대리를 구별하고 감독 기록 인계 | 런타임 실패/복구 신호, 권한·인계 정의 | 감시·재접속·선출에 기존 구조가 있나요? 명시적 신호와 임시 선출 방식부터 맞추고 세부값은 같이 정하면 어떨까요? |
| D08 · P1/P2 | 시체 잔존 정보와 선택 목표를 본 게임 진행과 연결 | cycle·잔존 정보, 감쇠/목표 정책 | 감쇠는 현재 임시값을 끌 수 있게 준비했습니다. 실제 정책과 목표 점수는 기본 연결 뒤 맞추는 순서가 괜찮을까요? |

## 제안 형식과 다른 경우 같이 확인할 정보

각자 기존 형식이 있다면 입력·출력 예시 한 쌍, ID의 의미, 처리 대기와 완료의 구분, 수신자의 정보 범위를 먼저 공유해 주시면 좋겠습니다. 기능 이름이나 전송 기술은 그 자료에 맞춰 GM 쪽에서 바꿀 수 있습니다. 역할이나 게임 규칙에 영향을 주는 대안은 변경 이유와 함께 확인하고, 접점 표현만 다른 경우에는 대응표와 어댑터로 맞춰 보겠습니다.

아직 실제 구현이 없어도 먼저 제공 가능한 데이터 정의나 mock 응답이 있으면 GM 준비를 이어갈 수 있습니다. 제안 순서가 현재 개발 계획과 맞지 않는다면, 먼저 연결할 수 있는 구간과 후속 작업의 선결 요소를 알려 주시면 작은 연결 범위를 다시 잡겠습니다.

## 첫 연결에서 함께 확인해 보면 좋을 것

같은 사건에 2명 이상을 붙여 이동 → 탐색 → 추리 생략 한 사이클을 먼저 실행하는 것을 제안드립니다. 같은 game/agent/action ID가 엔진 결과·agent 기억·GM 원장에 연결되고, 새 단서의 제외 의미와 수신 범위가 유지되는지 보고 싶습니다. 실패와 생략도 완료로 집계하고 재전송은 추가 소비하지 않는지 확인하면, 세 구현이 같은 작업을 하는 근거를 실행 기록으로 남길 수 있을 것 같습니다.

그다음 정상 agent 간 탐문·응답, 장애/NPC/시체·GM 대리, 선택 목표 순으로 연결하는 방향을 생각하고 있습니다. 더 적절한 순서나 먼저 보여 줄 수 있는 접점이 있다면 의견 부탁드립니다. 제가 준비한 GM 형식도 그 의견을 바탕으로 조정하겠습니다.
